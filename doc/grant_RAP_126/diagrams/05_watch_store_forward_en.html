Galaxy Watch Store-and-Forward

How sensor data from the watch reaches the phone reliably — even when the watch screen is off

Phase 1 — Session active  ·  watch screen on  ·  1 Hz sampling
1
Galaxy Watchsensors
→
Galaxy Watchlocal file (WatchSampleStore)
Persist every reading to a durable file on the watch
HR · IBI · EDA written as JSON lines, one row per sample — append-only
2
Galaxy Watchsensors
→
Phonelive display
Stream live reading over MessageClient (best-effort)
Phone shows real-time values LIVE
Phase 2 — Screen off / Doze  ·  live stream pauses
3
Galaxy Watchsensors
→
Galaxy Watchlocal file (WatchSampleStore)
Sampling continues at 1 Hz — every reading still persisted
The durable file accumulates rows; no data is lost during Doze
4
Galaxy Watchsensors
→
Phonelive display
Low-rate HEARTBEAT sent every 30 s (at each Doze wake window)
Phone shows DOZING — "Watch dozing — buffering" instead of "Disconnected"
Phase 3 — Session end  ·  remote flush & handover
5
Phoneoperator app
→
Galaxy Watchcommand listener
Send FLUSH command
Watch wakes to handle it even if the app is not in the foreground
6
Galaxy Watchsensors (SDK buffer)
→
Galaxy Watchlocal file (WatchSampleStore)
Drain any screen-off samples still buffered in the SDK into the file
Must happen before reading the store — otherwise data sitting in the SDK buffer would be missed
7
Galaxy Watchlocal file (WatchSampleStore)
→
Phoneoperator app
Ship all stored rows as chunked DataItems
DataClient guarantees delivery even if the link drops mid-transfer — unlike the best-effort live stream
8
Galaxy Watchcommand listener
→
Phoneoperator app
Send FLUSH_COMPLETE (chunk count + row count)
Phone waits for this signal before it knows the full transfer has arrived
9
Phoneoperator app (WatchSessionDrainer)
Match each row to a scenario by timestamp window
Every flushed reading carries the exact moment it was taken on the watch.
A reading falls into the scenario whose recording window [startedAt → endedAt] contains that timestamp.
Readings that fall between scenarios or after the last scenario ended are discarded — no scenario was active at that moment.
Readings already written during live streaming are skipped (de-duplicated per scenario, per sensor type).
10
PhoneRoom database
Save matched rows into the database  (WATCH_HR · WATCH_IBI · WATCH_EDA)
Only rows that matched a scenario window and were not already present are inserted
11
Phoneoperator app
→
Galaxy Watchcommand listener
Send FLUSH_ACK:<maxTimestamp> — confirms what was stored
Watch truncates rows up to and including this timestamp
12
Galaxy Watchlocal file (WatchSampleStore)
Truncate acked rows — keep any un-acked tail
If the transfer was interrupted, the remaining rows are re-sent on the next flush
No reading is ever lost
The durable file on the watch accumulates every sample regardless of link state.
Doze gaps are transparent to the recording — the store survives them intact.
A partial or interrupted flush simply re-sends the un-acked tail next time.
